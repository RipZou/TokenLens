# HW3 Reflection

We split the repository setup, fixtures, classifier experiments, GitHub Issues, rules, and documentation between us, then combined the results. We used Cursor as the IDE harness. The measurable task was issue #5, the Anthropic token classifier. One fresh session worked without `AGENTS.md`. Another fresh session was told to follow `AGENTS.md` and `docs/PRD.md`. Both results are in `docs/hw3/before-after.md`.

## How the rules file connects the PRD and the prototype to code

The PRD says what the product must do: split each call into structural categories, keep the category totals equal to the provider's `input_tokens`, and mark a large disagreement as estimated. The prototype shows the dashboard, the call detail, the budget banner, and the one-time API key. Neither document says which folder the function lives in, what its arguments are, or that a failing test has to be committed before the implementation. A short feature request leaves those choices open. `AGENTS.md` is the place we write them down so the next session does not invent them again.

That showed up in the comparison. Both sessions scored 9/9 on the shared fixtures, and both honored retrieval tags and the sum invariant. Removing the rules file did not lower the fixture score, because `docs/PRD.md` and `fixtures/anthropic/` were still in the tree and the no-rules session used them. The prompts also differed: the no-rules prompt asked for a TypeScript function over five buckets, while the with-rules prompt named issue #5, the PRD, and the checklist. We recorded that limit in [39e9bb0](https://github.com/RipZou/TokenLens/commit/39e9bb0). The fixture score belongs to the shared scorer. The other gaps are the combined effect of the prompt, the PRD, the fixtures, and the rules file.

Those other gaps are still the useful part. The with-rules session put `classify` in `src/lib/classifier/`, used the signature `classify(request, usage, provider, countTokens)`, wrote Vitest tests under `tests/unit/`, and committed the failing test (`ef539bb`) before the implementation (`b36353b`). The no-rules session put one file at `src/classify.ts`, made the tokenizer argument optional, used `node:test`, and committed tests and implementation together. It also treated any gap of five tokens as overhead. A probe with ten local words and a billed total of 14, a 29% gap, came back `estimated: false` without rules and `estimated: true` with rules. The nine fixtures never separate "five tokens" from "five percent," so a perfect fixture score can still hide that mistake.

The rules file was also too willing to describe the future app as if it already existed. A session asked to touch the classifier could have scaffolded Next.js, Prisma, and empty folders. We split "what is in the repo now" from "what the later issues will build" in [087fb32](https://github.com/RipZou/TokenLens/commit/087fb32), and aligned prices, key ownership, and sample retention with the PRD in [186066c](https://github.com/RipZou/TokenLens/commit/186066c). The prototype's fake login and demo role switch stay labeled as prototype behavior, not production behavior.

After that pass, three holes from the comparison were still open. The sessions agreed on token totals only because they could read the fixtures, not because the rules said which strings to count. [f7fe59a](https://github.com/RipZou/TokenLens/commit/f7fe59a) now says to skip the structural keys `type`, `id`, `tool_use_id`, and `tl_category`, to count the remaining strings, and to require the caller to pass `countTokens`. The name `Breakdown` had no fields, so a flat map of counts could look finished. [655226b](https://github.com/RipZou/TokenLens/commit/655226b) pins `input`, `output`, `cache`, `estimated`, `raw`, and `usage` to the type in `src/lib/classifier/types.ts`. [0f5bf3e](https://github.com/RipZou/TokenLens/commit/0f5bf3e) adds the ten-versus-fourteen example so the next session cannot treat a four-token gap as overhead when it is 29% of the bill.

## How the Scrum setup organizes the AI work

The board, the two milestones, and the sixteen issues give each session a boundary. Sprint 1 is the path from sign-in through an ingested, classified call. Sprint 2 is the live dashboard, OpenAI, budgets, and docs. An issue title says what to do. The acceptance checklist says when to stop. The milestone says which week it belongs to. The status column says whether it is waiting, started, in review, or done. We used issue #5 for the experiment because its result can be scored: nine fixtures, the sum invariant, and the estimated flag.

The workflow rules in `AGENTS.md` match that board. One issue gets one branch. A test commit comes before the feature commit. A pull request names the issue and waits for the partner. That is what made the with-rules history readable: `test(classifier): ... (red)` and then `feat(classifier): ... (green)`. Without those instructions, the no-rules session still produced a working function, but the history does not show a failing test first.

The column name **In Reveiw** was missing an `i`. The assignment asks for **In Review**. A misspelled column is a real Scrum defect even when the cards are in the right places, because a grader looking for the required name will not find it. Renaming the option keeps the existing cards; it does not move them.

## What we would change for Sprint 2

We would add examples for the behavior the prototype only implies: a Developer creates a key only on their own project, a Viewer who creates a project gets 403, an SSE client reconnects with the last event id, and an 80% budget alert fires once rather than on every poll. We would assign owners so the story points stay balanced, and we would move cards when the work moves, including correcting the review column's spelling.

The next comparison should use the same product prompt on both sides and should include a fixture like the ten-versus-fourteen case, so the score itself catches a flat token threshold. The rules should stay short. When a session repeats a mistake, we add one concrete rule and say why in the commit, which is what `f7fe59a`, `655226b`, and `0f5bf3e` do.
