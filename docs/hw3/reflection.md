# HW3 Reflection

We divided the repository setup, fixtures, classifier experiments, GitHub Issues, rules and documentation between us, then combined the results. We used Cursor for the AI-assisted development and compared two implementations of the Anthropic token classifier.

This work showed us that a feature description leaves many decisions open. The PRD describes what users need, and the prototype shows the intended interface, but the AI also needs instructions about folders, permissions, tests and commits. AGENTS.md connects these details. For example, specifying who can create a key or change a budget is more useful than simply asking for role-based access. The rules also distinguish the prototype's simulated behavior from what the real application must implement.

Both versions passed all nine fixtures, so the comparison did not show a higher pass rate with rules. The differences were in how the work was organized. The with-rules version followed our folder structure and function signature, used Vitest, and committed failing tests before implementation. A separate calibration check also exposed a five-token versus five-percent threshold difference. Since both sessions could read the PRD and fixtures, and their prompts differed, these results cannot isolate the effect of AGENTS.md alone.

The review showed that our rules mixed the current classifier with the planned full-stack application. We separated those in [087fb32](https://github.com/RipZou/TokenLens/commit/087fb32), aligned permissions, prices and sample retention with the PRD in [186066c](https://github.com/RipZou/TokenLens/commit/186066c), and clarified the comparison's limits in [39e9bb0](https://github.com/RipZou/TokenLens/commit/39e9bb0). This made the instructions reflect what actually exists instead of encouraging the AI to assume missing features are already available.

The 16 Issues and two milestones give each AI task a clear scope. Acceptance checklists define completion, estimates support planning, and PRs connect changes to the work being tracked. For Sprint 2, we would add examples and tests for project ownership, SSE reconnection and repeated budget alerts. We would also assign task owners and keep the board aligned with actual progress. In future comparisons, we would use the same prompt and stronger boundary fixtures. The goal is to keep the rules short, specific and updated as we find problems.
